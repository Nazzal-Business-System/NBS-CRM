# Identity and authentication foundation

## Database boundary

This change defines 11 models: Person, User, Role, Permission, RolePermission, Team, TeamMember, Session, AuditLog, Currency, WorkspaceSettings. No tenant ID, CRM business entities, or dashboard data are introduced. User has one unique Person and one Role. Login email is canonical lowercase and unique; Person contact email is a separate, non-unique communication attribute.

`prisma/migrations/20261016000100_identity_foundation/migration.sql` was generated offline from an empty schema, then reviewed and extended with PostgreSQL CHECK constraints, a partial active-session index, and trigger guards. **It has not been executed.** UUID defaults are generated by Prisma; timestamps use timestamptz(3). Currency precision is 0–4, workspace ID must be 1, and timezone is validated against PostgreSQL timezone names. No currency or business timezone is hardcoded as a deployment default.

Durable identities use RESTRICT foreign keys, users are deactivated, and people/teams can be archived. Role grants cascade only with deletion of an unassigned custom Role; system roles/grants are guarded. Audit rows cannot be updated, deleted, or truncated through normal DML. Database owners can disable triggers: deploy with a separate migration owner and a least-privilege runtime role, excluding DDL and audit UPDATE/DELETE/TRUNCATE.

## Sessions and HTTP

- Passwords use Node scrypt N=131072, r=8, p=1, random 16-byte salts and 64-byte derived keys; stored work factors are bounded. Minimum 12 characters, maximum 1024 UTF-8 bytes. Unknown-user attempts perform the same scrypt work. No password, hash, cookie, token, or raw DB error is logged.
- Opaque session tokens contain 32 random bytes. Only SHA-256 hashes are stored. Each login creates a fresh token and revokes a supplied previous session atomically. Browser responses expose a separate, session-derived CSRF token, never the session token itself.
- Default idle timeout: 30 minutes; absolute timeout: 12 hours. Idle renewal cannot extend absolute expiry. Validation checks revocation, active/unarchived identity, security version, and fresh permissions/team membership, then conditionally touches the still-active session.
- Production cookie: `__Host-crm_session`, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. Development uses a separate non-Secure cookie for loopback HTTP. Production auth requires an HTTPS WEB_ORIGIN.
- Unsafe requests require exact WEB_ORIGIN and X-CRM-Request: 1; cross-site Fetch Metadata is rejected. Authenticated mutations also require X-CSRF-Token matching the session verifier. Login has origin/custom-header protection against login CSRF. Auth responses use Cache-Control: no-store.
- Login throttling is bounded and per-process (IP plus hashed account key); at most two scrypt verifications run concurrently. Configure trusted-edge/shared limits before scaling. The API deliberately does not trust arbitrary proxy forwarding headers.

AUTH_ENABLED defaults false. When enabled, API routes are POST /api/auth/login, GET /api/auth/me, POST /api/auth/logout and POST /api/auth/sessions/revoke-all. No login screen or administration endpoints are provided yet. The public page is an informational foundation shell, not a protected CRM workspace. Health never accesses the database; Prisma is initialized lazily only for explicitly enabled auth operations/bootstrap.

## Permissions and administration

Permission keys and scope semantics live in packages/shared/src/permissions.ts. OWN covers the owner; TEAM includes own records and explicit active team membership; ALL covers the deployment. A missing capability always denies. Future subject-linked records must also enforce parent visibility, including in selectors, exports and reports.

Administration service boundaries reload the actor inside a serializable transaction with a common PostgreSQL advisory lock. Delegation cannot exceed the actor's grants/scope. Role assignment requires a separate capability. Delegated administrators cannot assign protected system roles; own-role edits and self role/activation changes are prohibited. System roles are immutable through ordinary service calls. Last-active-admin removal is guarded both by service policy and PostgreSQL triggers. Password/role/activation changes increment the user's security version, revoke affected sessions, and append an audit record atomically. Serialization conflicts fail closed; callers may retry the entire operation after reauthorization.

These services are not exposed as CRUD endpoints yet. Future user/team mutations must use the same transaction/authorization conventions; do not add direct Prisma writes from routes. New permission catalog entries and protected administrator grants need an explicit reviewed data migration after initial bootstrap.

## Initial administrator

Bootstrap is a manual CLI, not an HTTP route, seed or startup hook. It is not run as part of this task. It requires BOOTSTRAP_ADMIN=1 and JSON on non-interactive stdin, then locks and verifies an empty identity foundation. It creates the permission catalog, protected administrator role, Person/User, supplied Currency, singleton settings and audit atomically. Reruns refuse if users/roles/settings exist.

Only after separately authorizing/applying the migration in an isolated database, provide a protected stdin stream to `npm run admin:bootstrap -w @nbs-crm/api`. Input fields: name, email, password, currency { code, name, minorUnits }, timezone and locale (en/ar). Use a secret manager or restricted temporary input source; never put credentials in command arguments, shell history, examples, logs or tracked files. Remove BOOTSTRAP_ADMIN immediately afterward. Then enable AUTH_ENABLED. Never use the offline placeholder URL as a real deployment credential.

## Verification limits and next steps

Offline tests cover cryptography, session lifecycle, CSRF/origin controls, scope/delegation, administrative guard paths, bootstrap gates and environment precedence. Mocks exercise application authorization without a DB. Offline Prisma validation/client generation and production builds are separate checks. Migration SQL and triggers still require actual replay, rollback/recovery and concurrent mutation tests in an explicitly authorized disposable PostgreSQL instance. No claim of live database integration is made.

Before real deployment: complete those integration tests, provision least-privilege roles, HTTPS/proxy rules, shared rate limits as needed, session retention cleanup, operational monitoring, backup/restore procedures and a protected login/admin UI. MFA and password-recovery flows are later work.
